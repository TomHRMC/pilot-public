# React Engineer Implementation Prompt — Standard Inclusions

**Purpose**: This file is the authoritative checklist and template guide for any AI agent creating a Pilot React Engineer implementation prompt. Every prompt targeting the `pilot-react-engineer` mode MUST include all sections marked **REQUIRED**. Sections marked **CONDITIONAL** apply only when the described condition is true.

**Location**: `frontend/react-engr-std-prompt-inclusions.md`
**Consumed by**: Pilot Architect mode when writing implementation prompts
**Last updated**: 2026-07-28

> **Cross-reference**: This file is the _prompt template_ companion to the mode's _hard rules_ in [`.roo/rules-pilot-react-engineer/react-engineer-rules.md`](../.roo/rules-pilot-react-engineer/react-engineer-rules.md). The rules file is the authority (§1–§36); this file translates those rules into the sections a prompt must contain. When the two conflict, the rules file wins.

> **Confirmed stack (2026-07-28)** — cite where a rule depends on a version:
> Next.js 16.2 (App Router) · React 19.2 with the **React Compiler** (`babel-plugin-react-compiler@1.0.0`) · TanStack Query v5 · Zod v4 · React Hook Form 7 (`@hookform/resolvers` v5) · Tailwind v4 · Vitest 2 + Testing Library (web/`packages/ui`) · Jest (jest-expo) + Testing Library RN (mobile) · MSW 2 · pnpm 9 + Turborepo. ## 1. MANDATORY STOP Section (REQUIRED)

Every prompt MUST open with a `⚠️ MANDATORY STOP: Read These First` section immediately after the header block. This is not optional and must be the first substantive content the engineer reads.

```markdown
## ⚠️ MANDATORY STOP: Read These First

Before writing a single line of code, read:

- **[`.roo/rules-pilot-react-engineer/react-engineer-rules.md`](../.roo/rules-pilot-react-engineer/react-engineer-rules.md)** — in full
- **[`dev-docs/architecture-design/batch-designs/batch-[FE-BN]-design.md`](link)** — every section (A–I) ← omit if no design doc
```

**Always call out the highest-risk rules for the specific batch.** Common critical rules to pick from:

```markdown
Critical rules for this batch:

- **Rule 1.1**: Before writing ANY hook or API call, verify the endpoint exists in `backend/openapi_schema_map.md`. If it is NOT there → **STOP and ask Tom**.
- **Rule 1.2**: Do NOT invent URL patterns or parameter names. Every shape comes from `openapi.json` or the design doc (which was authored from `openapi_schema_map.md`).
- **Rule 1.3**: Run `pnpm sync-api-types` before starting — all TypeScript types for backend payloads come from `@pilot/shared-types`, never hand-written interfaces.
- **Rule 2**: All API calls use `apiClient` from `@pilot/shared-api` (**not** `@/lib/api-client` — that module does not exist). `fetch()` is permanently banned for `/api/v1/...` calls. Related exports in the same package: `isAxiosError`, `LIST_PAGE_SIZE`, `queryClient`.
- **Rule 3**: SSE endpoints require `?token=JWT` — browser `EventSource` cannot send `Authorization` headers.
- **Rule 7**: Check `packages/ui/src/index.ts` before creating any new component — `<LoadingState>`, `<ErrorState>`, `<EmptyState>`, `<RoleGate>`, `<InFlightSyncIndicator>`, `<TierPickerCard>`, `<SettingControl>` are all available.
- **Rule 8**: No new npm dependencies without first checking what is already installed in `package.json`.
- **Rule 9**: Route files in `apps/web/src/app/(authed)/` MUST be thin server components — no `"use client"`, no data fetching. All logic goes in feature components.
- **Rule 10**: If ANY test fails during your work — even one that appears to be pre-existing or caused by a previous batch — **you must fix it before declaring the batch done**. There is no "not my fault" exception. If you cannot identify the root cause → STOP and ask Tom.
- **Rule 11 (React Compiler — rules §32)**: The web app runs React 19.2 with the React Compiler enabled. Do NOT hand-write `useMemo`/`useCallback`/`React.memo` for render-perf — the compiler handles it. Keep components pure (never mutate props/state/hook-returns during render). Narrow identity-only exceptions still apply (a value passed to a `useEffect` dep array or a widely-consumed `Context`).
- **Rule 12 (TanStack Query v5 — rules §33)**: Object-form API only (`useQuery({ queryKey, queryFn })`). `gcTime` not `cacheTime`; `isPending` not `isLoading`. Structured, colocated query keys that include every `queryFn` variable. Set `staleTime` deliberately for reference data; `placeholderData: keepPreviousData` for paginated lists; invalidate (don't hand-patch) after mutations.
- **Rule 13 (Zod v4 + RHF — rules §34)**: Form validation is Zod v4 via `@hookform/resolvers/zod`. Use top-level format helpers (`z.email()`, `z.uuid()`) not `z.string().email()`; the unified `error` param not `message`/`invalid_type_error`. Zod is for form input — infer API payload types from `@pilot/shared-types`, never re-derive by hand.
- **Rule 14 (server vs client — rules §35)**: Authenticated data fetching stays **client-side** (`apiClient` + TanStack Query in `"use client"` components). Never fetch tenant data in a Server Component or Route Handler — the Amplify/Cognito session is browser-held and will 401 server-side.
- **Rule 15 (WCAG 2.2 AA — rules §36)**: Every new surface must satisfy Focus Not Obscured, Target Size (≥24×24px), Accessible Authentication (allow paste), Consistent Help, Redundant Entry, modal focus management, and non-color-only errors. Backs the axe-core DoD gate.
```

Include only the rules relevant to the specific batch. Do not list all 15 every time if only 4 apply — but Rules 1.x (verify endpoint), 2 (`apiClient`), and 10 (fix every failure) apply to nearly every batch.

## 3. Pre-Work: Sync API Types (REQUIRED — unless batch is purely UI with no new hooks)

Every prompt that touches or creates any TanStack Query hook MUST include `pnpm sync-api-types` before any other work.

````markdown
## Pre-Work: Sync API Types

```bash
cd <repo>/frontend
pnpm sync-api-types
```

This runs two steps: it `cd`s into `backend/`, activates the venv, runs `python export_openapi_json.py` to refresh `openapi.json`, then runs `openapi-typescript` to regenerate `packages/shared-types/src/api-schema.d.ts`. Because it re-exports the spec first, the generated types always match the **live backend code** — not a stale checked-in `openapi.json`. All backend payload types must come from `@pilot/shared-types` — never from hand-written interfaces (except stubs clearly marked `// TODO: delete when pnpm sync-api-types delivers this type`).

Consume types via the `components` root (rules §1.3):

```typescript
import type { components } from "@pilot/shared-types";
type QuoteResponse = components["schemas"]["QuoteResponse"];
```

> **If `pnpm sync-api-types` fails** because the backend endpoint is not yet deployed → note the affected hooks, write stubs, and document as companion backend tasks.
````

## 7. MSW Handlers (CONDITIONAL — when endpoints are not yet ready or new domain handlers are added)

When a batch has companion backend tasks, or when new domain handler files are created:

````markdown
## MSW Handlers for Missing Endpoints

For each endpoint in the Companion Backend Tasks list, create or extend an MSW handler file so development and tests can proceed without a live backend.

**Step 1 — Check which handler file to extend or create:**

```bash
# Web handlers:
find frontend/apps/web/src/mocks/handlers -name "*.ts" | head -20
cat frontend/apps/web/src/mocks/handlers/index.ts

# Mobile handlers:
find frontend/apps/mobile/mocks/handlers -name "*.ts" | head -20
cat frontend/apps/mobile/mocks/handlers/index.ts
```

**Step 2 — Create/extend the handler file:**

```typescript
// apps/web/src/mocks/handlers/myFeatureHandlers.ts
import { http, HttpResponse } from "msw";

export const myFeatureHandlers = [
  http.get("/api/v1/your-endpoint", () =>
    HttpResponse.json({ field1: "value", field2: null }),
  ),
  http.post("/api/v1/your-endpoint", async ({ request }) => {
    const body = (await request.json()) as any;
    return HttpResponse.json({ ...body, id: "mock-id" });
  }),
];
```

**Step 3 — Register in the barrel `index.ts`:**

```typescript
// apps/web/src/mocks/handlers/index.ts
import { myFeatureHandlers } from "./myFeatureHandlers";

export const handlers = [
  ...existingHandlers,
  ...myFeatureHandlers, // ← ADD THIS — without this line, the handler is never used
];
```

> **This step is mandatory.** Creating a handler file without registering it in `index.ts` means the handler is never loaded — tests will fall through to unhandled request warnings.

Always check the existing `index.ts` before adding — never create a duplicate `http.get` for a path that already has a handler.
````

## 8. Platform-Specific Rules Reference (REQUIRED — call out the platform for this batch)

Every prompt MUST explicitly state which platform(s) the batch touches. Different platforms have different mandatory constraints.

### 8.1 Web (`apps/web`) — Next.js App Router Rules

````markdown
### Platform: Web (`apps/web`) — Mandatory Constraints

- **Route files are thin server components**: `app/(authed)/path/page.tsx` files must NOT have `"use client"`, must NOT fetch data, must NOT contain logic. One line: `return <FeatureComponent />;`
- **Feature components own logic**: All `"use client"`, hooks, state, and data fetching belong in `features/[domain]/components/` or `features/[domain]/hooks/`
- **Component placement rule**: Generic/reusable → `packages/ui/`. Domain-specific web → `apps/web/src/features/[domain]/`. Shared types → `packages/shared-types/`
- **RBAC gating**: Any page restricted to specific roles MUST wrap its content in `<RoleGate permission="...">` from `@pilot/ui/role-gate`. Do NOT implement custom role checks inline.
- **State lifecycle patterns**: Use `<LoadingState>`, `<ErrorState>`, `<EmptyState>` from `@pilot/ui/states` — these are the canonical lifecycle display components.
- **SSE connections**: Include `?token={jwt}` in the EventSource URL. Implement with `useEffect` + cleanup. Never use SSE inside a TanStack Query `queryFn`.
- **React Compiler (React 19.2)**: Do NOT hand-write `useMemo`/`useCallback`/`React.memo` for render-perf — the compiler memoizes automatically. Keep components pure. `eslint-plugin-react-hooks` (v5+) enforces rules-of-react in `pnpm lint`; fix purity violations rather than disabling the rule. (rules §32)
- **TanStack Query v5**: Object-form only (`useQuery({ queryKey, queryFn })`); `gcTime` not `cacheTime`; `isPending` not `isLoading`. Colocate a `*_QUERY_KEY` constant / key factory that includes every `queryFn` variable. `placeholderData: keepPreviousData` for paginated lists; invalidate in `onSettled` after mutations. (rules §33)
- **Zod v4 + React Hook Form 7**: Validate forms with `zodResolver`; use top-level `z.email()`/`z.uuid()` and the unified `error` param. Infer API types from `@pilot/shared-types` — never re-derive a backend shape as a Zod type. (rules §34)
- **Test framework: Vitest + `@testing-library/react`** — use `vi.mock()` (not `jest.mock()`), `toBeInTheDocument()` assertions, `import { describe, it, expect, vi } from "vitest"`.
- **Mock Next.js in web tests**: Any component using `next/navigation` or `next/link` requires mocking in tests:
  ```typescript
  vi.mock("next/navigation", () => ({ usePathname: () => "/dashboard" }));
  vi.mock("next/link", () => ({
    default: ({ href, children, ...rest }: any) =>
      React.createElement("a", { href, ...rest }, children),
  }));
  ```
````

### 8.2 Mobile (`apps/mobile`) — Expo/React Native Rules

````markdown
### Platform: Mobile (`apps/mobile`) — Mandatory Constraints

- **WatermelonDB schema changes**: Always update `database/schema.ts` AND create the corresponding `database/models/[ModelName].ts`. Read an existing model (e.g., `LotoCheck.ts`, `Expense.ts`) for the exact pattern before creating a new one.
- **Sync wiring**: Any new WatermelonDB table that syncs must be registered in `database/sync/orchestrator.ts`. Read the orchestrator before adding new table entries.
- **Tab suppression**: Any new non-tab screen in `app/(tabs)/[feature]/sub-screen.tsx` must be suppressed in `app/(tabs)/_layout.tsx`. Read `_layout.tsx` before adding suppressions.
- **Dual-path hooks**: Hooks that call backend APIs must implement offline fallback. Use `@react-native-community/netinfo` to check connectivity — never assume online.
- **Styling**: Use design tokens from `constants/style-constants.ts`. Never hardcode hex colors or pixel values inline.
- **No new npm dependencies** without confirming availability in `frontend/apps/mobile/package.json` first.
- **Test framework: Jest (jest-expo preset) + `@testing-library/react-native`** — use `jest.mock()`, `.toBeTruthy()` / `.not.toBeNull()` assertions, `fireEvent.press()` (not `userEvent.click()`).
- **Type check command**: `pnpm --filter mobile build` runs `tsc --noEmit`. There is NO separate `check-types` script for mobile — `build` is the mobile type-check step.
- **Expo Router must be mocked in all screen tests**:

  ```typescript
  const mockPush = jest.fn();
  jest.mock("expo-router", () => ({
    useRouter: () => ({ push: mockPush, back: jest.fn(), replace: jest.fn() }),
    useLocalSearchParams: () => ({}),
    router: { push: mockPush, back: jest.fn() },
    Link: ({ children }: { children: React.ReactNode }) => children,
  }));
  beforeEach(() => {
    mockPush.mockClear();
  });
  ```

- **WatermelonDB must be mocked in all tests** (real DB writes are banned):
  ```typescript
  jest.mock("../../../database", () => ({
    database: {
      write: jest.fn((fn) => fn()),
      get: jest.fn(() => ({
        create: jest.fn((fn) => {
          const record = { id: "mock-id", localSyncStatus: "pending" };
          fn(record);
          return Promise.resolve(record);
        }),
      })),
    },
  }));
  ```
````

### 8.3 Shared UI (`packages/ui`) — Component Library Rules

```markdown
### Platform: Shared UI (`packages/ui`) — Mandatory Constraints

- **Exports must be added to `src/index.ts`**: Any new shared component that other apps will consume must be exported from `packages/ui/src/index.ts`. Read the index file before exporting.
- **`permissions.ts` is additive only**: When adding new `PermissionKey` entries, read the full current file, then ADD to the type union and `ROLE_PERMISSION_MAP`. Never remove or rename existing keys — it breaks all callers.
- **No platform-specific imports**: `packages/ui` must not import from `next/*`, `expo/*`, or any platform-specific library. It must work in both Next.js and React Native contexts.
- **Run `@pilot/ui` tests after every permissions.ts change**: Permission changes affect RBAC system-wide. Verify immediately after each modification.
- **Test framework**: `packages/ui` uses Vitest — use `vi.mock()`, `describe/it/expect` from vitest.
```

## 9. Test Writing Standards (REQUIRED — for any batch adding new components or hooks)

Every prompt that adds new frontend functionality MUST specify test requirements.

````markdown
## Test Requirements

### TanStack Query — Required Setup for All Tests

**Always use `retry: false`** on the QueryClient in tests — default retry=3 causes test timeouts:

```typescript
function createWrapper() {
  const queryClient = new QueryClient({
    defaultOptions: {
      queries: { retry: false },
      mutations: { retry: false },
    },
  });
  return ({ children }: { children: React.ReactNode }) => (
    <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>
  );
}

// In renderHook:
const { result } = renderHook(() => useMyHook(), { wrapper: createWrapper() });

// In render:
render(<QueryClientProvider client={new QueryClient({ defaultOptions: { queries: { retry: false } } })}><MyComponent /></QueryClientProvider>);
```

**Never share a QueryClient instance across tests** — always create a fresh one per test.

### MSW in Tests — Correct Setup

```typescript
import { setupServer } from "msw/node"; // ← node, not browser
import { http, HttpResponse } from "msw";

const server = setupServer(...handlers);
beforeAll(() => server.listen({ onUnhandledRequest: "warn" }));
afterEach(() => server.resetHandlers()); // ← critical — resets per-test overrides
afterAll(() => server.close());

// Per-test override:
server.use(
  http.get("/api/v1/resource", () => HttpResponse.json([], { status: 500 })),
);
```

**Never mock `apiClient` directly** — MSW intercepts at the HTTP level and is the only correct approach.

### RBAC Testing — `AuthContext.Provider` Pattern (Web)

For web tests that verify role-based visibility, use the `AuthContext.Provider` directly:

```typescript
import { AuthContext } from "@pilot/ui/auth";
import type { AuthContextValue, PilotRole } from "@pilot/ui/auth";

function makeAuthValue(role: PilotRole): AuthContextValue {
  return {
    user: {
      id: "u1",
      email: "test@example.com",
      role,
      tenantId: "t1",
      displayName: "Test",
      accessToken: "tok",
    },
    isAuthenticated: true,
    role,
    signIn: vi.fn(),
    confirmMfaChallenge: vi.fn(),
    signOut: vi.fn(),
    refreshSession: vi.fn().mockResolvedValue("tok"),
  };
}

function renderAs(role: PilotRole) {
  return render(
    React.createElement(
      AuthContext.Provider,
      { value: makeAuthValue(role) },
      React.createElement(MyComponent),
    ),
  );
}

it("tech does NOT see financial section", () => {
  renderAs("tech");
  expect(screen.queryByText("Revenue")).not.toBeInTheDocument();
});
```

### Test Resilience Rule (MANDATORY — applies to every test, new or modified)

Frontend tests run against MSW mock handlers that intercept HTTP requests. The resilience rule for frontend tests is about **mock data isolation and MSW handler scope** — ensuring tests don't interfere with each other through shared mock state:

- **Never rely on module-level mock data shared across tests.** If a test needs a specific API response shape, override it inline using `server.use(...)` within that test. Reset with `server.resetHandlers()` in `afterEach`.
- **Never assert on a total count from an API response unless the MSW handler is scoped to return exactly that count for this test.** The global MSW handler may return a list of items from a fixture; asserting `expect(items).toHaveLength(N)` will break if the fixture changes. Always assert by ID or specific content: `expect(screen.getByText(fixture.customer_name)).toBeInTheDocument()`.
- **Never mutate shared fixture objects.** Fixture objects defined at module level (e.g., `const mockCustomers = [...]`) must be treated as read-only. If a test needs a modified version, create a copy: `const modified = { ...mockCustomers[0], status: 'overdue' }`.
- **Integration tests that render a full page must use MSW to control the exact data returned** — they cannot depend on real backend state (this is why `NEXT_PUBLIC_USE_MOCK_AUTH=true` is the default for tests). Never write a frontend integration test that hits a real API endpoint.
- **Per-test MSW override pattern** (for testing specific states like errors or edge cases):
  ```typescript
  it("shows error state when API fails", () => {
    server.use(
      http.get("/api/v1/customers", () =>
        HttpResponse.json({ error: "server error" }, { status: 500 }),
      ),
    );
    render(<CustomersPage />, { wrapper: createWrapper() });
    expect(screen.getByRole("alert")).toBeInTheDocument();
    // server.resetHandlers() in afterEach restores the default handler
  });
  ```

### Test Anti-Patterns — Never Do These

| ❌ Wrong                                                        | ✅ Correct                                                            |
| --------------------------------------------------------------- | --------------------------------------------------------------------- |
| Module-level `render(<Component />)` outside a test             | Always inside `it()` / `test()` blocks                                |
| Shared `QueryClient` instance across tests                      | Create a fresh one per test via `createWrapper()`                     |
| Missing `retry: false` on QueryClient                           | Always set both `queries.retry: false` and `mutations.retry: false`   |
| `jest.mock("@pilot/shared-api", ...)` to mock apiClient         | Use MSW at the HTTP level — never mock `apiClient` directly           |
| Asserting on total item count (`expect(items).toHaveLength(N)`) | Assert by specific IDs or content from the MSW fixture                |
| Mutating shared module-level fixture objects                    | Always create copies: `{ ...fixture, field: 'newValue' }`             |
| Hardcoded mock IDs                                              | Use dynamic IDs from MSW response or factory functions                |
| Skipping tests because "it's just a UI batch"                   | Every new surface needs at minimum a render + RBAC test               |
| Forgetting to mock Expo Router in mobile screen tests           | Always `jest.mock("expo-router", ...)` in mobile screen tests         |
| Real WatermelonDB writes in mobile tests                        | Always mock `database` module in mobile tests                         |
| Forgetting to register new MSW handler file in `index.ts`       | Always add `...newHandlers` to the barrel export                      |
| Web test using `.toBeTruthy()`                                  | Web uses `toBeInTheDocument()` — `.toBeTruthy()` is for mobile        |
| Mobile test using `toBeInTheDocument()`                         | Mobile uses `.toBeTruthy()` — `toBeInTheDocument()` is web/jsdom only |

### 10.1 Test Exit Hygiene (Jest + MSW open handles — house standard, TEST-UPLIFT-1C 2026-08-28)

**The mobile `test` script carries `--forceExit`** (`apps/mobile/package.json`: `"test": "jest --passWithNoTests --forceExit"`). Every prompt's Phase 1/Phase 2 commands keep using `pnpm --filter mobile test` unchanged — the flag lives in the script.

- **Why**: MSW 2.x + Jest has a known upstream open-handle issue — `server.close()` does not fully drain the Node.js event loop, so the CLI would hang **5+ minutes AFTER all tests pass** ("Jest did not exit" / "worker process has failed to exit gracefully"). Symptom: tests take 1–3s each but the command never returns.
- **Safety property**: `--forceExit` runs **all tests to completion first** and only truncates the post-run event-loop drain. It cannot skip or shorten test execution — a suite reporting N passed ran N tests.
- **Never "fix" a hang by deleting `server.close()` / `resetHandlers()`** — those keep per-file MSW isolation intact; the flag handles the drain.
- **Diagnosing a REAL hang** (a test never completes — not the post-run drain): run `pnpm --filter mobile test -- --detectOpenHandles` to find the leaked handle (unclosed WS / DB connection / timer) and fix the source instead of masking it.
- **Web / `packages/*` (Vitest)**: unaffected — Vitest `run` mode exits natively. Do not add Jest flags to Vitest packages.

### 10.2 Known Benign Test Warnings (verified 2026-08-28 — do not chase)

Both warnings below were investigated by the React Engineer and verified benign by the Architect — tests pass correctly. **Do not burn batch time "fixing" them.** The proper fixes are tracked under each.

**W1 — `[apiClient] fetchAuthSession threw: Error [ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING_FLAG]` (mobile Jest; logs once per MSW-intercepted request)**

- **Cause**: [`packages/shared-api/src/client.ts`](packages/shared-api/src/client.ts)'s request interceptor does `await import("aws-amplify/auth")`. Jest (jest-expo) does not run with `--experimental-vm-modules`, so Node's **native** dynamic `import()` fails. The interceptor's `catch` block logs the warn and lets the request proceed without a JWT attached.
- **Why benign**: the request proceeds normally, and MSW handlers match on URL/method — they ignore `Authorization`. Tests never exercise real Cognito JWT attachment. Production is unaffected (the warn is `NODE_ENV !== "production"`-guarded; Metro/browser bundles handle dynamic import natively). It became visible only after TEST-UPLIFT-1C: the 10 banned files previously mocked `@pilot/shared-api` wholesale, so the interceptor never executed. Suppression via `jest.mock("aws-amplify/auth")` / `moduleNameMapper` / mock files does **NOT** work — Node's native `import()` bypasses Jest's module system entirely.
- **Proper fix (tracked → BE-TESTS-MAINT)**: (a) run Jest with `--experimental-vm-modules`, or (b) refactor `client.ts` to a static import with a conditional guard, or (c) add a Jest transformer converting dynamic imports to `require()` for the shared-api package.

**W2 — `transform-class-properties` / `transform-private-methods` loose-mode warnings (mobile Babel)**

- **Cause**: `babel-preset-expo@54` bundles its own class-properties/private-methods plugins with `loose: true`, conflicting with the top-level `assumptions` block in `babel.config.js` (our config already uses the recommended top-level `assumptions` API per react-engineer Rule 28).
- **Why benign**: cosmetic only — class-field transformation works correctly. Known upstream Expo SDK 54 issue; unfixable without forking `babel-preset-expo`.
- **Proper fix**: resolves upstream with Expo SDK 55+ — evaluate at the next native-dep window (BG-UP-1 / MOB-B11).

## 18. Seed-Data Awareness for New Backend Fields (CONDITIONAL — FE batch consuming a new schema field)

When a React batch consumes a backend field that a companion backend batch just added (e.g., a new `priority`, `site_type`, or `job_type` field), the prompt MUST include this awareness note. Frontend batches do not edit seed scripts, but their MSW fixtures and tests must reflect that the field is now real (and seeded with varied values), not the old hardcoded fallback.

```markdown
### Seed-Data Awareness (new backend field)

The backend companion batch added `[field]` to the seed data (both platform defaults and scenario rows) — it is no longer a hardcoded frontend fallback. Therefore:

- **Remove any hardcoded fallback** in the hook/normalizer that faked this field (e.g. `priority: "standard"` hardcoded in a `normalizeX` function). Read the real value from the API response.
- **Update MSW fixtures** so at least one mock record carries a **non-default / varied** value for `[field]` — a fixture where every row has the same value cannot prove the filter/display works. Mirror the seed scenario's variety (e.g. one `emergency`, one `rush`, rest `standard`).

```

// ❌ dead weight — the compiler already memoizes

## Marketing Site — `react/no-unescaped-entities` Apostrophe Fix

**Problem**: The marketing site (`apps/marketing`) had 22 pre-existing `react/no-unescaped-entities` ESLint errors — raw apostrophes in JSX text nodes (e.g., `I'm`, `don't`, `That's`). The `eslint --max-warnings 0` lint gate was already failing before any C-B13 work.

**Why `'` and `'` don't work with `apply_diff`/`write_to_file`**: The Roo Code tool layer HTML-decodes entities in SEARCH/REPLACE blocks, so `'` in the REPLACE block becomes the literal `'` character — making SEARCH and REPLACE identical (no-op). Python `sed`-style scripts also fail because VSCode's file watcher reverts external writes when the file is open in an editor tab.

**Solution — the `{"'"}` JSX expression pattern**: Wrap apostrophes in a JSX string expression: `I{"'"}m` renders as `I'm` in the browser and satisfies the ESLint rule because the apostrophe is inside a JS expression, not raw JSX text. This pattern works with `apply_diff` and `write_to_file` because the tool doesn't interpret `{"'"}` as an HTML entity.

**When to use**: Any time you encounter `react/no-unescaped-entities` errors in marketing site files (or any file where `apply_diff` is the editing tool). Replace `word's` → `word{"'"}s` in JSX text nodes only (not in JS string literals like `desc: "it's gone"` — those are fine).

**Bulk fix script** (for many errors at once): If there are many errors, use the ESLint JSON report as the source of truth and a Python script that patches by exact line:column. The script must handle UTF-16 column offsets (ESLint columns are UTF-16 code unit based, not Python code point based — surrogate pairs like emoji cause a discrepancy). See `/tmp/fix_apostrophes.py` from the C-B13 session for the reference implementation. **Important**: close the file in VSCode before running the script, or the file watcher will revert the write.
````
