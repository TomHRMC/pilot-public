## Purpose

This is the single living record of **architecturally significant decisions** for Pilot for Trades. It replaces the retired 18-document traceability matrix (archived 2026-06 at `dev-docs/traceability-archive-06-2026/` _(private)_).

**Why only decisions live here**: every other traceability artifact duplicated a source of truth that is already generated or queryable (OpenAPI spec, live DB via MCP, the launch plan, the model map). A hand-maintained catalog that duplicates a generated source is guaranteed to drift and gives false confidence. **Decision rationale is the one class of information that exists nowhere else** — so it is the one thing we keep alive.

### What belongs in this log (the Michael Nygard / AWS Well-Architected bar)

Record an ADR only when **all** of these are true:
1. The decision is **architecturally significant** — it affects system structure, a key quality attribute (cost, security, latency, availability), or is **hard to reverse**.
2. **Multiple viable options existed.** If the choice was obvious, no ADR is needed.
3. The decision **crosses a boundary** — it affects more than one sub-project, agent, or master doc.

Do **not** log: routine implementation choices, anything already captured by a generated source (a new endpoint → OpenAPI; a new column → live DB/JSON schema; a batch's completion → launch plan), or descriptive facts with no decision behind them.

## ADR Entry Format

Each ADR uses this lightweight Nygard-style template. Copy it for every new entry.

```markdown
### ADR-NNNN — <Short imperative title>
- **Date**: YYYY-MM-DD
- **Status**: Proposed | Accepted | Superseded by ADR-XXXX | Deprecated
- **Context**: What forces are at play (cost cap, latency budget, security, scaling trigger, vendor constraint)?
- **Options considered**: A / B / C (one line each — why they were viable)
- **Decision**: The option chosen, stated as a directive.
- **Consequences**: Trade-offs accepted, follow-on obligations, what this makes harder.
- **Affects**: sub-projects / agents / master docs that must reflect this decision.
- **Supersedes / Superseded by**: ADR link, if applicable.
```

**Numbering**: monotonically increasing `ADR-0001`, `ADR-0002`, … Never reuse a number. A reversed decision is marked `Superseded` and a NEW ADR captures the replacement — never edit history in place.

## Decisions

> **Note**: ADR-0001 through ADR-0008 are *ratifications* of decisions originally made during the Pass 1–4 design phase (April–May 2026) and previously captured across the now-archived traceability matrix. They are re-stated here in Nygard form because they remain binding, boundary-crossing, and hard to reverse — exactly the decisions that must stay visible. Their granular source-doc extraction lives in the archive.

### ADR-0001 — Fargate-first compute (no EKS, no App Runner)
- **Date**: 2026-07-28 (ratifies design-phase decision ARCH-§1.1/§1.3)
- **Status**: Accepted
- **Context**: Fixed <$1,000/mo cost cap (~$888/mo MVP target at 100 customers). Need to run FastAPI, Celery workers, and the Next.js web dashboard without a control-plane tax. AWS App Runner was **sunset April 30, 2026** — no new services can be created on any AWS account.
- **Options considered**: (A) EKS — rejected, ~$73/mo control-plane cost + ops burden; (B) App Runner for Next.js SSR — no longer possible (sunset); (C) ECS Fargate for all container workloads — chosen.
- **Decision**: Run FastAPI, Celery (concurrency 2), and Next.js `pilot-web` all as ECS Fargate services on the shared `pilot-production` cluster. `pilot-web` is the 4th service (0.5 vCPU / 1024MB, port 3000), fronted by the existing ALB via a `Host: app.pilotfortrades.com` listener rule — zero marginal ALB cost.
- **Consequences**: One cluster to reason about; SSE connections consume a Fargate task thread each (see ADR-0004 scaling note); no serverless auto-idle for the web tier.
- **Affects**: DevOps agent, `infrastructure-constraints.md`, `mvp-arch.md §1`, `aws-infrastructure-as-built.md`.

### ADR-0002 — Owned GPU for all generative AI
- **Date**: 2026-07-28 (ratifies ARCH-§6.5)
- **Status**: Accepted
- **Context**: Voice AI (Whisper transcription + Llama intent parsing) and generative help chat would incur unbounded variable cost on cloud GPU/LLM APIs. Cost cap demands a fixed-cost inference path.
- **Options considered**: (A) OpenAI/Anthropic generative APIs — rejected, variable cost, cap risk; (B) cloud GPU rental — rejected, variable; (C) single owned EC2 `g4dn.xlarge` (NVIDIA T4) — chosen, flat ~$384/mo, unlimited inference.
- **Decision**: All generative AI runs on one owned `g4dn.xlarge` (Whisper :8080, Ollama :11434), sized to ~500 tenants before a second instance. **Only** exception: OpenAI `text-embedding-3-small` for pgvector document embeddings (~$7/mo) — never for generative chat.
- **Consequences**: We own GPU ops/patching; scaling is manual (see ADR-0004 trigger); a single instance is a capacity ceiling until the 500-tenant / p95 > 2.5s trigger.
- **Affects**: Voice AI Specialist, `infrastructure-constraints.md`, `scaling-logic.md`, `mvp-arch.md §6`.

### ADR-0003 — Single Multi-AZ RDS t4g.micro with pgvector HNSW
- **Date**: 2026-07-28 (ratifies ARCH-§2.1/§2.4)
- **Status**: Accepted
- **Context**: Need durable multi-tenant Postgres + vector similarity for AI help/context, within cost cap and the 100-connection micro-tier limit.
- **Options considered**: (A) distributed/Aurora — rejected on cost; (B) separate vector DB (Pinecone/pgvector-on-separate-instance) — rejected, extra cost + sync complexity; (C) single Multi-AZ `db.t4g.micro` with `pgvector` HNSW in-database — chosen.
- **Decision**: One Multi-AZ `db.t4g.micro`; `pgvector` HNSW (`vector_cosine_ops`) on conversation embeddings; pool `pool_size=5, max_overflow=10` to stay under 100 connections.
- **Consequences**: Scale by Storage Autoscaling first, then instance class only when `work_mem`/connections are exhausted (never proactively). Connection budget is tight — every long-lived connection (SSE) counts.
- **Affects**: Python Engineer, DevOps, `scaling-logic.md`, `mvp-arch.md §2`.

### ADR-0004 — SSE for real-time; WebSocket reserved for Voice
- **Date**: 2026-07-28 (ratifies ARCH-§7.9 adjacent / frontend standards)
- **Status**: Accepted
- **Context**: Dispatch board, calendar conflicts, notifications, and SMS threads need server push. WebSockets add bidirectional-connection overhead we only need for streaming audio.
- **Options considered**: (A) WebSocket everywhere — rejected, heavier + browser `EventSource` simplicity lost; (B) polling — rejected, latency + DB load; (C) SSE for all real-time, WebSocket **only** for Voice AI streaming — chosen.
- **Decision**: SSE for all real-time surfaces. Because browser `EventSource` cannot send `Authorization` headers, **all SSE endpoints accept `?token=JWT`**. WebSocket is used exclusively for the Voice AI pipeline.
- **Consequences**: Each SSE connection holds a Fargate task thread → scaling trigger at ~1,000 customers to shift to Redis Pub/Sub broadcast. Token-in-query-string requires the same auth rigor as headers.
- **Affects**: React Engineer, Web UI Designer, Python Engineer, `scaling-logic.md`, `mvp-arch.md §7`.

### ADR-0005 — Tenant-scoped `select()`; `db.get()` banned
- **Date**: 2026-07-28 (ratifies FIND-132, 2026-05-10)
- **Status**: Accepted
- **Context**: `db.get(Model, pk)` returns any row by PK regardless of tenant ownership — an IDOR vector. FK integrity ≠ tenant ownership.
- **Options considered**: (A) post-fetch tenant check — rejected, row already read into memory; (B) rely on FK integrity — rejected, doesn't prove ownership; (C) always filter by `tenant_id` in the query — chosen.
- **Decision**: `db.get()` is **permanently banned** on any model with a `tenant_id`. Every fetch uses `select().where(Model.id == pk).where(Model.tenant_id == current_user.tenant_id)`; return **404** (never 403) on miss to prevent enumeration.
- **Consequences**: Slightly more verbose queries; every design spec/code review must enforce it.
- **Affects**: Python Engineer, QA, `pilot-architect-methods.md §7.1`, `pilot-python-engineer-methods.md §6.2`.

### ADR-0006 — Idempotency by default with natural-key fallback
- **Date**: 2026-07-28 (ratifies ARCH-§7.6)
- **Status**: Accepted
- **Context**: Mobile app operates offline up to 72 hours; retries and duplicate submissions are expected on reconnect.
- **Options considered**: (A) client-side dedup only — rejected, unreliable; (B) idempotency key only — insufficient for 72h offline (key TTL 24h); (C) `Idempotency-Key` (24h TTL, SHA-256 body hash, pessimistic lock) **plus** per-operation natural-key fallback on a 7-day window — chosen.
- **Decision**: All POST/PATCH/PUT/DELETE accept `Idempotency-Key`; offline-executable mutations also carry natural keys (e.g., time_entry `(user_id, job_id, clock_in_at)`).
- **Consequences**: Every offline-capable endpoint must define its natural key in its design doc; extra table (`idempotency_key`) + middleware.
- **Affects**: Python Engineer, React Engineer (mobile), `mvp-arch.md §7.6`.

### ADR-0007 — OpenAPI as the frontend contract
- **Date**: 2026-07-28 (ratifies ARCH-§11.4)
- **Status**: Accepted
- **Context**: Hand-written TypeScript interfaces drift from the backend and cause silent runtime breaks.
- **Options considered**: (A) hand-authored types — rejected, drift; (B) GraphQL — rejected, adds a layer, off-pattern; (C) generate types from FastAPI OpenAPI — chosen.
- **Decision**: `backend/export_openapi_json.py` → `openapi.json` → `pnpm sync-api-types` → `packages/shared-types/src/api-schema.d.ts`. This is the **only** source of FE types. Running `pnpm sync-api-types` is the mandatory BE→FE handoff signal after every backend batch.
- **Consequences**: Backend batches must regenerate OpenAPI before FE work starts; marketing app (raw fetch) is exempt.
- **Affects**: Python Engineer, React Engineer, `mvp-arch.md §11`, both engineer inclusion files.

### ADR-0008 — Pre-commit staleness check (409-and-refresh)
- **Date**: 2026-07-28 (ratifies ARCH-§7.9, §16.3 pattern)
- **Status**: Accepted
- **Context**: Concurrent edits (dispatch reschedule/assign, calendar/QB/mobile conflict resolve, quote approve/reject) can silently clobber newer data.
- **Options considered**: (A) last-write-wins — rejected, data loss; (B) hard locks — rejected, offline/mobile incompatible; (C) optimistic expected-version check returning 409 + refreshed payload — chosen.
- **Decision**: Write endpoints accept `expected_updated_at` / `expected_*_version` fields and return **409 with the refreshed payload** on mismatch; client shows "this has been updated"; voice path re-reads updated context aloud.
- **Consequences**: Every concurrent-edit endpoint must expose an expected-version field; a locked `§16` platform pattern in `packages/ui/`.
- **Affects**: Python Engineer, React Engineer, Web UI Designer, `mvp-arch.md §16.3`.

### ADR-0010 — RBAC role-vocabulary alignment + owner-only invoice editing
- **Date**: 2026-07-28
- **Status**: Accepted
- **Context**: Surfaced during BILLING-B1 (Part B) design. Two independent RBAC registries exist and had drifted apart: (1) the **frontend** explicit-key registry [`packages/ui/src/role-gate/permissions.ts`](../../frontend/packages/ui/src/role-gate/permissions.ts) with roles `owner | office_staff | tech | operator`; (2) the **backend** wildcard registry — the live `tenant_user_role` table seeded by [`seed_core.py`](../../backend/migrations/scripts/seed_core.py) with roles `owner | office_staff | technician | accountant`, evaluated by [`core/permissions.py:has_permission()`](../../backend/core/permissions.py) (`*`, `resource.*`, `*.action`). The role vocabularies do not match (`tech`↔`technician`, `operator`↔`accountant`), and the FE `operator` is a *manager* set while the BE `accountant` is *read-only* — nearly opposite. Separately, `permissions.ts` was missing the `invoices.update` key entirely, so `<RoleGate permission="invoices.update">` denied **everyone including owner**, blocking the BILLING-B1 payment-schedule editor. The backend already enforces `invoices.update` correctly (owner via `*`; office_staff has create+view but not update; technician denied) — verified live via `postgres-local` MCP. Note: [`api/schemas/roles.py`](../../backend/api/schemas/roles.py) is **request/response schemas only**; its permission arrays are Swagger `json_schema_extra` examples with **zero runtime effect** — it is not a source of RBAC truth.
- **Options considered**: (A) grant `invoices.update` to office_staff too (spec's original assumption) — rejected: office_staff is intentionally read-mostly (support/CRM), must not edit invoices; (B) spin a dedicated RBAC-B1 batch to add the key across FE+BE+seed+migration — rejected: backend already correct, so the only real change is one FE registry line, too small for a batch; (C) add `invoices.update` to the FE registry **owner set only** (folded into the BILLING-B1 Part B React work) and park the FE↔BE role-vocabulary reconciliation as an explicit P2 item — **chosen**.
- **Decision**: (1) **Invoice editing (`invoices.update`) is owner-only.** office_staff = read-mostly (create + view, no update), the future `accountant` = read-only (`*.view`), tech/technician excluded. This matches the live backend seed exactly — **no backend change, no migration, no batch**. (2) The `invoices.update` key is added to the frontend `PermissionKey` union and the `owner` role set **only**, folded into the BILLING-B1 Part B React prompt (removing the temporary `invoices.create` gate + `// TODO(invoices.update)`). (3) **Role-vocabulary alignment is deferred to the P2 RBAC-hardening line**: rename FE `operator` → `accountant` (and **replace** its manager permission set with the read-only accountant set — not a string swap), and align FE `tech` → `technician` with the backend. `roles.py` requires no grant edit ever (examples only).
- **Consequences**: BILLING-B1 unblocks with a one-line FE change and no backend risk. The FE↔BE role-name/permission divergence remains until the P2 batch — until then, the FE `operator` role has no backend counterpart (any tenant user seeded `operator` would fail backend permission lookups), which is acceptable because no tenant is seeded with the `operator` role. The P2 rename is a boundary-crossing, hard-to-reverse change (touches FE registry, live seed, a forward migration, and any assigned users) and must itself be designed as a proper batch.
- **Affects**: React Engineer, Web UI Designer, Python Engineer, Architect; `permissions.ts`, `seed_core.py`, `batch-billing-b1-ui-design-spec.md`, `batch-billing-b1-react-engr-prompt.md`, `pilot-launch-plan.md` (P2 PLAT-DEBT).

### ADR-0011 — Self-serve credential creation via Cognito self-sign-up feeding the Post-Confirmation Lambda
- **Date**: 2026-07-29
- **Status**: Accepted (approved by Tom with batch SIGNUP-GA-1, 2026-07-29)
- **Context**: GA self-serve onboarding (Gap G1) requires the signup flow to create an authentication credential. Today Cognito self-registration is disabled and the wizard collects no password; Beta is concierge (Tom runs `AdminCreateUser`). **Email is the only Cognito↔RDS join key** — MCP-verified: the `user` table has no `cognito_sub` column. We must not weaken the "signup state machine is the single account-birth path" invariant (`mvp-arch.md §4.4`) nor duplicate the prod Post-Confirmation Lambda's tenant/user creation. `tenant_signup` is keyed by `tenant_id` (no `id` PK) and does not persist owner email. A Post-Confirmation trigger fires on **every** confirmation in the pool — across four user types (platform owner, platform user, tenant owner, tenant user) — so a naive "always create a tenant" is wrong for three of them.
- **Options considered**: (A) **Backend-orchestrated `AdminCreateUser`** — backend calls Cognito with boto3; gives the backend powerful Cognito admin IAM and forces it to handle/relay a password — rejected on security surface. (B) **Cognito self-sign-up (`SignUp` via Amplify) feeding the existing Post-Confirmation Lambda** — client creates the credential, email-verifies, the existing Lambda writes tenant+user to RDS, the wizard attaches by email — chosen. (C) **Hosted UI** — hand auth to Cognito's redirect UI — rejected on UX/brand fit and least wizard control.
- **Decision**: **Option B.** Re-enable Cognito self-sign-up (email+password, email verification) which feeds the **existing** Post-Confirmation Lambda. The Lambda is specified as a **3-path user-provisioning router** keyed on `email`: **Path 1** existing/platform `user` → no-op (types i/ii); **Path 2** pending `tenant_user_invite` → attach `user`+`tenant_user` to the invite's tenant (type iv); **Path 3** neither → create `tenant`(placeholder name)+owner `user`+`tenant_user` (type iii, self-serve GA). The wizard's step 1 becomes **resolve-or-attach by email** (never forks a second tenant) and overwrites the placeholder `tenant.name` with the real business name. Backend takes **no** Cognito admin IAM and never handles the password. Self-registration is re-enabled but rate-limited + Turnstile-guarded at the `/sign-up` edge. The router is built in full now; only the type-(iii) product surface ships in SIGNUP-GA-1 (types i/ii/iv UIs are follow-on batches `PLATFORM-ADMIN-1` / `TEAM-INVITE-1`).
- **Consequences**: (+) Reuses the prod Lambda bridge — one account-birth path, honoring `mvp-arch.md §4.4`. (+) No new backend IAM; password stays in Cognito; standard first-login/MFA challenge flow (aligns with MFA-WIRE-1, no duplication). (+) $0 cost delta (within Cognito free MAU tier at 100 users). (+) Building the full router once protects types i/ii/iv from misfires before their UIs exist. (−) Requires a **DevOps-owned** Cognito pool config change (re-enable self-sign-up) + Terraform + Lambda packaging, and the wizard step-1 semantics change to resolve-or-attach (must be idempotent + race-safe). (−) The Lambda must **never raise to Cognito** (an unhandled exception fails the confirmation) — the reason [ADR-0012](#adr-0012--drop-global-tenant-name-uniqueness-tenantname-is-display-only) drops the tenant-name unique constraint. (−) Email remains the sole Cognito↔RDS join; a future `cognito_sub` linkage is a separate, larger decision, explicitly not taken here. Does **not** address founders-billing G3 (`stripe_customer_id`) — tracked separately.
- **Affects**: DevOps (Cognito pool Terraform + Post-Confirmation Lambda), Python Engineer (`signup.py`, `tenant_signup.py`, Lambda handler), React + RN (`SIGNUP-GA-1-FE` password/`SignUp`), Architect; `pilot-founder-onboarding-process.md` (§5 + close G1/G6), `mvp-arch.md §4.4`, `aws-infrastructure-as-built.md`, `aws-cognito-prod-setup.md`, `batch-signup-ga-1-design.md`.
- **Supersedes / Superseded by**: none. **Related**: [ADR-0012](#adr-0012--drop-global-tenant-name-uniqueness-tenantname-is-display-only) (drops the constraint that would otherwise let Path 3 raise inside the Lambda).

### ADR-0012 — Drop global tenant-name uniqueness (`tenant.name` is display-only)
- **Date**: 2026-07-29
- **Status**: Accepted (approved by Tom with batch SIGNUP-GA-1, 2026-07-29)
- **Context**: MCP-verified live state: `public.tenant` has a UNIQUE index `tenant_name_key` on `name`, but **no foreign key anywhere targets `tenant.name`** — every FK into `tenant` references `tenant.id`. The only code that treats the name as unique is [`auth.py::_signup_impl`](../../backend/api/routes/auth.py) (a `Tenant.name` pre-check raising `400`), whose sole test is [`test_auth.py`](../../backend/tests/test_auth.py). Two constraints collide with product reality and with [ADR-0011](#adr-0011--self-serve-credential-creation-via-cognito-self-sign-up-feeding-the-post-confirmation-lambda): (a) two legitimately distinct businesses can share a name (e.g. "ABC Plumbing, LLC" in MD and DE); (b) the SIGNUP-GA-1 Post-Confirmation Lambda must insert a placeholder tenant name and **must never raise to Cognito** — a unique-violation there could strand the user's confirmation. Guarding a valueless constraint required collision-proof UUID-suffix machinery in the Lambda.
- **Options considered**: (A) **Keep `tenant_name_key`** + build collision-proof placeholder naming (SELECT-check + UUID-fragment suffix + unique-violation retry) in the Lambda — rejected: adds an exception path to a trigger that must never throw, all to defend a constraint with zero referential value. (B) **Replace with a narrower uniqueness** (per-state or per-owner) — rejected: no requirement justifies it and it reintroduces the throw risk. (C) **Drop the constraint entirely; `tenant.name` becomes a display-only attribute** — chosen.
- **Decision**: Drop `tenant_name_key` (`op.drop_constraint("tenant_name_key", "tenant", type_="unique")`, folded into the SIGNUP-GA-1 blank migration). `tenant.name` is display-only; identity/dedup is by `tenant.id` and (for signup) by owner email. The Lambda's Path 3 inserts the friendly placeholder `"{email-local-part}'s Company"` **unconditionally** (no collision check). The `_signup_impl` `Tenant.name` pre-check is removed and `test_auth.py` retired (also serves the G6 reconciliation).
- **Consequences**: (+) Removes the only exception path that could strand a Cognito confirmation; eliminates the collision-proof-suffix complexity. (+) Allows legitimately-identical business names across regions. (+) Admin/support tenant lookups already disambiguate by id/email, not name — no human-facing regression. (−) Hard to reverse in practice: once duplicate names exist, re-adding the unique constraint (migration downgrade) will fail — accepted and documented. (−) Any future code must not assume `tenant.name` is unique.
- **Affects**: Python Engineer (migration, `_signup_impl`, Lambda placeholder), QA (`test_auth.py`), Architect; `pilot-db-schema-v2.6h.json` (blueprint regen via `schema_manager.py`), `mvp-arch.md §4.4`, `batch-signup-ga-1-design.md`.
- **Supersedes / Superseded by**: none. **Related**: [ADR-0011](#adr-0011--self-serve-credential-creation-via-cognito-self-sign-up-feeding-the-post-confirmation-lambda).

### ADR-0019 — Stripe Connect Express + direct charges for tenant customer payments
- **Date**: 2026-08-28
- **Status**: Accepted (approved by Tom, 2026-08-28 — STRIPE-CONNECT-1 model-decision gate, launch plan §3.6)
- **Context**: When a contractor's customer pays an invoice on the public `/i/[token]` page, funds must land in the **contractor's own Stripe account** — Pilot is not a payment processor, and [`stripe_payment_intents.py`](../../backend/services/stripe_payment_intents.py) originally charged everything on Pilot's platform key. The 2026-07-24 planning cycle narrowed the account-model choice to **Express vs Standard** (Custom rejected out of hand — Pilot would host KYC-adjacent onboarding UI and handle sensitive identity data, wrong for MVP). UI-FIX-2F (✅ 2026-08) built the Connect foundation — Account Links hosted onboarding, `tenant.stripe_connect_account_id`, `stripe_account=` routing, 402 not-connected guard — but created accounts with **`type="standard"`** ([`stripe_connect.py`](../../backend/api/routes/stripe_connect.py) line 143). The Account Links pattern and direct-charge routing are model-agnostic; the account **type** was the open decision.
- **Options considered**: (A) **Express** — chosen: platform creates the account for the contractor via API; Stripe-hosted onboarding (Account Links), KYC, payouts, 1099s, and a simplified Stripe-hosted Express dashboard; lowest onboarding friction for a non-technical electrical-contractor founder cohort; no independent API access for the connected account (platform calls via `stripe_account=`). (B) **Standard** — rejected: contractors must independently create and fully manage a Stripe account before linking (OAuth); heaviest onboarding friction and drop-off risk for the founder cohort; the only material upside (contractor's fully independent full Stripe dashboard) is not worth the friction at MVP — target founder-cohort contractors typically have no Stripe account. (C) **Custom** — rejected: Pilot hosts all onboarding UI and touches KYC data; unacceptable liability/complexity for MVP.
- **Decision**: **Stripe Connect Express with direct charges.** (1) STRIPE-CONNECT-1 flips `Account.create(type="standard")` → `type="express"` with explicit `capabilities` (`card_payments`, `transfers` — Express requires capability requests). (2) Charges stay **direct charges** on the connected account (`stripe_account=`); the contractor pays Stripe's processing fees; **no application-fee/platform-fee model in MVP** (destination-charge fee layering is a Phase 1.5 decision). (3) The sandbox test connected account `acct_XXXXXXXXXXXX` remains Standard — direct charges behave identically across account types, so mixed-type coverage is retained for free. (4) Reversal cost is acknowledged: accounts created under one model cannot be silently converted (Standard↔Express migration is a Stripe-support-mediated process), which is why the decision is recorded before any production connected account is created — prod has zero Connect accounts today.
- **Consequences**: (+) Founder onboarding to card payments is a ~10-minute Stripe-hosted flow with no Stripe-signup prerequisite. (+) KYC/payout/1099 liability stays with Stripe; Pilot never handles identity documents. (+) UI-FIX-2F's Account Links + routing build carries forward unchanged except the type flip + capability requests. (+) Express's no-independent-API-access posture matches the product model (Pilot is the system of action). (−) Contractors get the simplified Express dashboard, not the full Stripe dashboard — accepted; dispute response and payouts remain Stripe-hosted surfaces, and MVP dispute handling is owner-notification only (STRIPE-CONNECT-1 scope). (−) A future application-fee model requires the Phase 1.5 destination-charge/fee-layering design — not blocked by this ADR.
- **Affects**: [`batch-stripe-connect-1-design.md`](batch-designs/batch-stripe-connect-1-design.md) (A1 account-type alignment, §G Q1/Q2), `pilot-launch-plan.md` _(private)_ §3.6 (model-decision gate cleared), Python Engineer (stripe_connect.py), DevOps (Connect webhook endpoint registration + `STRIPE_CONNECT_PLATFORM_KEY` / `STRIPE_CONNECT_WEBHOOK_SECRET` secrets), `pilot-operations.md` _(private)_ §11, [`stripe-pricing-config.md`](../integrations/stripe/stripe-pricing-config.md) §8.
- **Supersedes / Superseded by**: none. **Related**: [ADR-0013](#adr-0013--three-pathway-sms-model-repurpose-cxxxxxx-as-pilot-sender-platform-notifications) (same "platform mediates the vendor relationship" posture).

### ADR-0020 — Project hibernation — deep AWS teardown to a single-digit cost floor; all DNS canonized at Cloudflare
- **Date**: 2026-09-07
- **Status**: Accepted (Tom, 2026-09-07 session). The author asked to bring hosting cost down to single-digit dollars a month (from about $102), keep only what is needed to serve the static S3/CloudFront page, drop the bastion and RDS (after a full schema and data backup to the local dev database), and noted that DNS management and registration had already moved from GoDaddy and Route 53 to Cloudflare.
- **Context**: Tom is pausing development for a few months with zero customers live (pre-founder; prod carries only seeded/test data). The existing [`profile-off.sh`](../../infrastructure/scripts/profile-off.sh) cost floor (~$102/mo — RDS, Redis, NAT, ALB, S3/CloudFront, R53, bastion EIP always-on) is 10–50× Tom's target for a hiatus whose only public surface requirement is a static marketing hold page. Separately, Tom moved **all** domain registration + DNS for `pilotfortrades.com` and `p4tsites.com` to Cloudflare (extending ADR-0014's posture to the apex domain), leaving the Route 53 hosted zone vestigial and several docs stale.
- **Options considered**: (A) **`profile-off.sh` as-is** (~$102/mo) — rejected: an order of magnitude over target for serving one static page. (B) **Deep teardown to ~$7–9/mo** — chosen: destroy all bill-bearing compute/network/data/monitoring resources via targeted `terraform destroy`; keep only S3+CloudFront+ACM (hold page), the TF state backend, Cognito + Lambdas ($0), Secrets Manager + KMS (~$5.40 — zero-friction restart), ECR + log groups (~$0.60); RDS destroyed with `skip_final_snapshot=true` (Tom's local `pg_dump` is the data backup; restart provisions per ADR-0016); GPU terminated including the models EBS volume (userdata re-pulls models free); marketing site replaced by a single self-contained static `index.html` hold page (no forms) with CloudFront 403/404 → hold-page mapping; `api.`/`app.`/`*.p4tsites.com` DNS deleted to NXDOMAIN while MX/DKIM/SPF/DMARC/SendGrid/ACM-validation records are preserved; Route 53 zone deleted. (C) **Scorched (~$2–3/mo)** — deferred option, documented in design §G-5: additionally export+delete secrets and schedule KMS deletion; not the default because the SendGrid API key is unrecoverable post-creation and $4.40 buys a zero-friction restart. (D) **Migrate hosting to Cloudflare Pages** — rejected: abandons TF-managed, profile-script-integrated hosting for <$2/mo and adds a migration surface.
- **Decision**: (1) **HIBERNATE-1** executes option B per [`batch-hibernate-1-design.md`](batch-designs/batch-hibernate-1-design.md); sustained hibernation spend ≤ $9/mo, guarded by a $10 AWS Budgets alert. (2) The mandated running posture in [`infrastructure-constraints.md`](../../.roo/rules-pilot-architect/infrastructure-constraints.md) (Multi-AZ RDS, Fargate-first, owned GPU, ElastiCache) is **suspended, not amended**, for the hibernation window; restart restores it in full via `terraform apply` + ADR-0016 data provisioning + the runbook §21 Restart Runbook (design §F Restart Contract). (3) **All DNS is canonized at Cloudflare** for both domains; the Route 53 hosted zone is deleted and docs referencing Route 53 as authoritative are corrected in-batch. (4) The Next.js marketing app source remains frozen in git untouched; the hold page lives at `infrastructure/marketing-hold/` (outside `deploy-marketing.yml` trigger paths) and is deployed by direct S3 sync. (5) Data authority during hibernation = Tom's verified local dev DB `pg_dump` + the seed system (ADR-0016); no RDS snapshot is retained.
- **Consequences**: (+) ~$660–700/mo → ~$7–9/mo sustained; the hiatus is financially negligible. (+) Restart is fully documented (design §F + runbook §21) and estimated at ~1 working day. (+) Email deliverability, both domains, both ACM certs, and the Cognito user base survive the hiatus intact. (The Cognito pools were later deleted for publication, 2026-11-14 — see PROVENANCE.md.) (−) Restart carries real re-provisioning time: GPU model re-pull (~20 min), DNS recreation, secret refresh, and a fresh empty RDS that must be re-seeded (no prod snapshot — accepted per Tom; prod held only seed/test data). (−) Telnyx numbers and Stripe test webhook endpoints may need re-provisioning/re-enabling at restart. (−) The profile scripts and `.infra-state.env` are stale during hibernation; `generate-infra-state.sh` re-runs at restart. (−) Month-1 bill shows prorated teardown charges; the single-digit target applies month 2+.
- **Affects**: [`batch-hibernate-1-design.md`](batch-designs/batch-hibernate-1-design.md) (execution spec), `pilot-launch-plan.md` _(private)_ §1.1 Ord 33 / §3.33, [`aws-infrastructure-as-built.md`](../devops/aws-infrastructure-as-built.md) (hibernation state banner), [`aws-env-mgmt-ops-plan.md`](../devops/aws-env-mgmt-ops-plan.md) (§10-mandated update), [`aws-ops-runbook.md`](../devops/aws-ops-runbook.md) (§17.2 Cloudflare zones + §20 restart runbook), [`infrastructure/scripts/README.md`](../../infrastructure/scripts/README.md) + [`profile-off.sh`](../../infrastructure/scripts/profile-off.sh) (hibernation note + stale R53 comment fix), ADR-0014 (Cloudflare posture extended to the apex domain).
- **Supersedes / Superseded by**: none; **amended by [ADR-0021](#adr-0021--hibernation-tier-selection--scorched-elected-secretskmsecr-destroyed-cognito-lambda-detach-gates-kms-deletion)** (tier selection — scorched elected over the option-B default). **Related**: [ADR-0014](#adr-0014--new-domains-on-cloudflare-registrar--dns-only-posture-p4tsitescom-apex-redirects-to-marketing-at-the-cloudflare-edge) (extended), [ADR-0016](#adr-0016--schema-restore-provisioning--environment-aware-seeds-migrations-become-ddl-only) (restart data path).

### ADR-0021 — Hibernation tier selection — scorched elected (secrets/KMS/ECR destroyed); Cognito Lambda detach gates KMS deletion
- **Date**: 2026-09-07
- **Status**: Accepted (Tom, 2026-09-07). Secrets were stored and backed up externally before secrets, KMS keys and ECR images were deleted; all watchdog / CloudWatch triggers were removed to bring spend near zero; two full database and schema backups and the DNS zone exports and Terraform state backup were kept in the private repository (not in this snapshot).
- **Context**: ADR-0020 (same day) designed HIBERNATE-1 with a ~$7–9/mo default keep-list (option B: retain the 11 Secrets Manager entries + KMS CMK + ECR images for a zero-friction restart) and documented a ~$2–3/mo scorched option (C) as non-default. Tom ratified all nine design §G decisions and **elected option C**, completed every preservation artifact himself (DB backup pair → `dev-docs/db-design/dbbackups/` _(private; not in this snapshot)_; Cloudflare zone exports → `dev-docs/devops/godaddy-cloudflare-archive/` _(private; not in this snapshot)_; TF state pull → `infrastructure/terraform/environments/production/2026.09.07-p4t-prod-data.json` _(private; not in this snapshot)_), and directed that all CloudWatch watchdogs be destroyed. One new technical constraint surfaced at ratification: the kept ($0) Cognito user pool's **CustomEmailSender Lambda decrypts via the CMK** (COGNITO-EMAIL-1), and the dormant Lambdas read Secrets Manager values — deleting KMS/secrets with triggers still attached would permanently break pool auth flows.
- **Options considered**: (A) Keep ADR-0020's option-B default — rejected by Tom: his external secrets backup removes the re-entry friction the $5.40/mo was buying. (B) **Scorched with a mandatory Cognito-detach gate** — chosen. (C) Scorched without detaching (delete KMS with triggers attached) — rejected: pool auth emails fail permanently; detach is a 1-minute config call with a documented rollback posture.
- **Decision**: (1) **Scorched tier elected** — destroy all 11 secrets (`--force-delete-without-recovery`), the KMS CMK (`schedule-key-deletion` 7-day, strictly after secrets + RDS + GPU EBS are gone), and all ECR images (repo shells stay, TF-managed, $0). Sustained hibernation ≈ **$1–3/mo AWS** (+ $2 EUM TFN ⇒ ≤ ~$5 total). (2) **Mandatory ordering gate**: detach the 3 Cognito Lambda triggers via the full-carry `update-user-pool` (`--lambda-config "{}"` **with** `--auto-verified-attributes email` + `--device-configuration …` carried — the 2026-09-04 reset-prone-blocks incident lesson) BEFORE any KMS/secret deletion; pool falls back to `COGNITO_DEFAULT`. (3) **All CloudWatch watchdogs destroyed** (11 alarms, dashboard, 7 log groups, SNS topic); a single AWS Budgets $10 alert is retained at **$0** (Budgets free tier — not a CloudWatch trigger). (4) Preservation artifacts are canonized at the committed repo paths above (superseding the design's v1.0 to-do steps). (5) Restart deltas vs ADR-0020 §F: secrets re-entered from Tom's external backup under a **new CMK (new ARN — TF rewires)**; ECR images rebuilt + pushed (+30–60 min); Cognito triggers re-attached per runbook §14.5. (6) End-of-batch checkpoint = Tom's commit + merge to `dev` after the verification board is green.
- **Consequences**: (+) Sustained AWS spend drops to roughly the cost of the CloudFront/S3 static path alone — the hiatus is financially noise. (+) The ordering gate prevents the one irreversible mistake in the scorched path (a bricked user pool). (+) All restoration inputs (data, DNS, state, secrets) now exist in the private repository or the author's external store; none are published in this snapshot. (−) Restart gains three chores vs option B: ~15 min of secret re-entry, ~30–60 min of image rebuilds, and the Cognito re-attach smoke — accepted. (−) The old CMK's 7-day deletion window is a one-way door for anything still encrypted with it — the destroy ordering (secrets/RDS/EBS first) makes that set empty. (−) CloudWatch deploy history is discarded — accepted (git is the history).
- **Affects**: [`batch-hibernate-1-design.md`](batch-designs/batch-hibernate-1-design.md) v1.1 (§B.3 keep/destroy lists, §B.3 ⚠️ detach block, Phase 6.3b, §F, §G.v1.1), `pilot-launch-plan.md` _(private)_ §3.33, [`aws-ops-runbook.md`](../devops/aws-ops-runbook.md) §14.5 (re-attach) + §20 (restart), [`aws-cognito-prod-setup.md`](../devops/aws-cognito-prod-setup.md) (rollback posture).
- **Supersedes / Superseded by**: amends [ADR-0020](#adr-0020--project-hibernation--deep-aws-teardown-to-a-single-digit-cost-floor-all-dns-canonized-at-cloudflare) (tier selection only — the hibernation posture, DNS canonization, and restart model stand). **Related**: [ADR-0016](#adr-0016--schema-restore-provisioning--environment-aware-seeds-migrations-become-ddl-only).
